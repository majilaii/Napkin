# RLS Audit — 2026-04-24

Produced by TICKET-034. Enumerates every RLS-enabled table and its current SELECT
policy shape as of the migrations applied. `USING (true)` policies are flagged with
a justification; all others note the scoping logic.

---

## Tables with intentional `USING (true)` (public read, non-UGC)

### `restaurants`
- **SELECT**: `USING (true)` on multiple policies ("Allow public read restaurants",
  "Restaurants are publicly readable", "restaurants readable"). Also allows `anon`.
- **Justification**: Restaurants are factual/public data (like Google Places metadata).
  Not user-generated content. Any authenticated or anonymous visitor may browse.

### `places`
- **SELECT**: `USING (true)` ("places_readable").
- **Justification**: Same as restaurants — factual place metadata, not UGC. No privacy
  concern.

## Tables with correctly scoped SELECT policies

### `entries`
- **Before TICKET-034 Migration B**: `entries_readable` `USING (true)` — BUG. Any
  authenticated user could read any row.
- **After Migration B**: `entries_select_v2` `USING (can_view_entry(entries))` — four
  branches: author / tablemate / companion / public-eligible-with-public-profile.
  `TO authenticated` only; anon users get no direct read.

### `entry_participants`
- **Before**: `entry_participants_select` `USING (true)` — BUG.
- **After**: `entry_participants_select_v2` `USING (user_id = auth.uid() OR EXISTS
  (SELECT 1 FROM entries e WHERE e.id = entry_id AND can_view_entry(e)))`.

### `entry_photos`
- **Before**: `entry_photos_select` — buggy policy referencing `table_members.user_id`
  (column does not exist; should be `member_id`). Silently returned empty for tablemates.
- **After**: `entry_photos_select_v2` `USING (EXISTS (SELECT 1 FROM entries e WHERE
  e.id = entry_id AND can_view_entry(e)))` — correct and consistent.
- **Note**: INSERT/DELETE policies unchanged (gate on entry ownership); these were correct.

### `entry_companions`
- **Before**: `entry_companions_read` — multi-branch (owner / self / tablemate) but
  inconsistent with `can_view_entry`; does not account for companion-only access on
  private entries where the tablemate branch would have been wrong.
- **After**: `entry_companions_select_v2` `USING (user_id = auth.uid() OR EXISTS
  (SELECT 1 FROM entries e WHERE e.id = entry_id AND can_view_entry(e)))`.
- **Note**: INSERT/DELETE policies unchanged.

### `profiles`
Multiple policies in OR:
- `profiles self access` — `USING (auth.uid() = user_id)` — own row.
- `profiles read table mates` — tablemates via shared table membership.
- `profiles read public` (from 20260423000000) — `account_privacy = 'public'`.
- **Assessment**: Correct. All three branches needed: self, tablemates (for Table
  UI joins), and public (for stranger/public-profile browsing and the `can_view_entry`
  public-branch EXISTS).

### `tables`
- `Members can view their tables` — `EXISTS (SELECT 1 FROM table_members WHERE
  table_id = tables.id AND member_id = auth.uid())`.
- **Assessment**: Correct. Tables are never public per doctrine.

### `table_members`
- `Members can view table members` — `is_table_member(table_id, auth.uid())`.
- **Assessment**: Correct. Members see other members of their Tables.

### `table_nights` (Rounds)
- `Members can view table nights` — `EXISTS (SELECT 1 FROM table_members WHERE
  table_id = table_nights.table_id AND member_id = auth.uid())`.
- **Assessment**: Correct. Round visibility gated on Table membership.

### `table_night_participants`
- `Members can view participants` — `EXISTS (SELECT 1 FROM table_nights JOIN
  table_members ON table_id = table_id WHERE table_night_id = id AND member_id = auth.uid())`.
- **Assessment**: Correct.

### `post_reactions`
- `post_reactions_select_table` — scope='table' AND viewer is table member.
- `post_reactions_select_public` — scope='public' AND `is_entry_publicly_eligible(target_id)`.
- **Assessment**: Correct. Two-scope model matches doctrine.

### `post_comments`
- `post_comments_select_table` — scope='table' AND viewer is table member.
- `post_comments_select_public` — scope='public' AND `is_entry_publicly_eligible(target_id)`.
- **Assessment**: Correct.

### `wishlist_items`
- `wishlist_items select policy` — `auth.uid() = user_id OR EXISTS (shared table
  member)`.
- **Assessment**: Correct. Tablemates can see each other's wishlists (needed for
  Table wishlist overlap feature).

### `lists`
- `lists_select` — `auth.uid() = owner_id OR privacy = 'public'`.
- **Assessment**: Correct. Per-list privacy toggle at creation; public lists are
  browsable by any authenticated user.

### `list_entries`
- `list_entries_select` — gates on parent list visibility (owner or list.privacy='public').
- **Assessment**: Correct. Inherits parent list privacy.

### `follows`
- `follows_read_own` — `follower_id = auth.uid() OR following_id = auth.uid()`.
- **Assessment**: Correct. You can see who you follow and who follows you; strangers'
  follow relationships are not exposed.

### `user_restaurant_status`
- `Users can view own status` — `auth.uid() = user_id`.
- **Assessment**: Correct. Private per-user status.

### `user_places`
- `user_places_own_access` — `auth.uid() = user_id`.
- **Assessment**: Correct.

- **Status**: Table appears to be a legacy predecessor to `entries`. The 2025-12-18
  migration drops `reviews` (`20251218140000_drop_reviews_table.sql`), but the
  remote schema (`20251201113055`) still references it — suggests it was dropped
  on prod but restored in the remote snapshot. Confirm with `\d reviews` against
  prod.
- **Action**: Out of scope (separate cleanup ticket per TICKET-034 non-goals). If
  the table exists on prod, the `USING (true)` policies on a legacy table are low
  risk (data is stale / unmaintained), but a cleanup ticket should drop the table.
