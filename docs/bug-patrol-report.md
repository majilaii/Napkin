## Critical (fix immediately)

1. **Duplicate-save resolution throws `unique_violation` and strands the card forever** — `supabase/migrations/20260603000700_fix_pass1.sql:396` (`fn_complete_import_job`) and `supabase/migrations/20260603000800_fix_pass2.sql:229` (`fn_correct_import_job`).
   `wishlist_items` has a UNIQUE index on `(user_id, restaurant_id)` (`supabase/migrations/20260420000000_wishlist_items.sql:16`). Both completion RPCs do a bare `UPDATE wishlist_items SET restaurant_id = p_restaurant_id WHERE job_id = ...` with **no `ON CONFLICT` / dedup**. When extraction (or a user correction) resolves to a restaurant the user **already** has a non-deleted wishlist row for, the UPDATE violates the unique index → the SECURITY DEFINER function raises → the whole transaction rolls back. Effect: the `import_jobs` row, the `wishlist_items` row, AND every `table_shares` row for that job stay `extraction_status='pending'`/`'needs_confirm'` permanently (they share the one transaction). `handleAsyncExtract` only logs `completeErr` (`supabase/functions/resolve-url/index.ts:825`), and `useCorrectImport.onError` rolls the optimistic patch back silently — so the card looks like nothing happened. This fires for the single most natural user action the feature invites: re-saving a spot you already saved. The spec's own AC ("a user re-saving a restaurant they already wishlisted hits the existing idempotent wishlist add") is therefore not met. **Fix direction:** in both RPCs, make the wishlist write conflict-aware — e.g. delete the just-created pending row and keep the pre-existing one, or `UPDATE ... ` then swallow `unique_violation` by deleting the dup pending row; mirror the same idempotency the old `wishlist` add path got via `upsert(..., onConflict)`.

2. **The async extractor's only authorization is `INTERNAL_CALL_SECRET`; if that prod secret is unset, every import job stays `pending` forever** — `supabase/functions/table-shares/index.ts:263` (sets `x-internal-secret` from `INTERNAL_CALL_SECRET`) and `supabase/functions/resolve-url/index.ts:926-928` (rejects `action=extract` without it). `create_import` fires `resolve-url[action=extract]` with the service-role key as bearer; resolve-url skips `auth.getUser` and authorizes solely via the shared secret. If `INTERNAL_CALL_SECRET` (and/or `ANTHROPIC_API_KEY`) is not set in prod Supabase secrets, the internal call 401/403s, the catch only `console.error`s (`table-shares/index.ts:280`), and the job never leaves `pending` — every capture shows "reading it…" indefinitely with no error. The smoke list documents this as a deploy-time requirement (`scripts/smoke/edge-functions.ts:121-128`) but **nothing verifies it at runtime**, and `table-shares`/`resolve-url[extract]` are not exercised by any smoke check. Since the ticket is already deployed: **verify both `INTERNAL_CALL_SECRET` and `ANTHROPIC_API_KEY` are actually set in the prod project** (`npx supabase secrets list --project-ref ftvmseaqwwlcxtdlvxxz`). If either is missing, the entire import pipeline is silently dead in prod despite shipping. Needs operational verification — cannot be confirmed from the repo.

## High (fix this sprint)

1. **URL captures (TikTok / Maps) cannot fan out to Tables — destination routing only exists for the screenshot/vision path** — `napkin-app/components/wishlist/ImportLinkSheet.tsx:289` and `:380-415`. The `DestinationPicker` (wishlist + multi-Table multi-select via `create_import`) is reached **only** when `source_type === 'screenshot' || 'vision'`. For a pasted TikTok or Maps URL, the sheet routes to `picking`/`confirming` → `handleSave` → the legacy `useWishlistAdd` single-wishlist path. So a URL save can never land a Table-feed share card or fan to multiple destinations, contradicting the AC "One save fans out to all ticked destinations." Functional gap, not a crash. **Fix direction:** route URL captures through the same `destination` → `create_import` path (or document that URL saves are wishlist-only by design and update the spec/AC).

2. **`table-activity` — the highest-churn read path in this ticket — is not in the smoke list** — `scripts/smoke/edge-functions.ts:68-140`. TICKET-060 rewrote the `fn_table_activity_page` RPC signature (added `p_coalesce_hours`, two new UNION streams) and added the entire share/float hydration block to the `table-activity` edge fn (`supabase/functions/table-activity/index.ts:438-578`). This is the function that renders the Table feed for every member. If the new RPC or hydration 500s in prod, no smoke check catches it and the auto-revert never triggers. CLAUDE.md: "when a postmortem traces a fire to an endpoint not in the list, add it." This one should have been added proactively given the blast radius. **Fix direction:** add a `table-activity` POST `{ table_id }` read check (needs a known seed table_id, like the existing `RESTAURANT_ID` env pattern) and a `wishlist list_personal` already-present sibling. Optionally add a `restaurant-history` verified-filter check.

3. **`restaurants` SELECT RLS was globally tightened to `verified OR created_by=auth.uid()` — confirm no anon-key client read silently loses rows** — `supabase/migrations/20260603000700_fix_pass1.sql:53` drops the old `USING (true)` policies and restricts reads. All *new* rows default to `verified` and all pre-existing rows were backfilled to `verified` (`20260603000000_restaurants_verification_owner.sql:28`), so only genuinely-unverified model ghosts are hidden — the intended H4 behavior, and every edge fn that reads via service-role re-applies an explicit `verification` filter. **Residual risk:** one client path reads `restaurants` directly via the anon key (`napkin-app/hooks/entries/useMySoloEntries.ts:47`), which is now RLS-subject. It's almost certainly fine (solo entries point at verified restaurants, and the user's own ghosts remain visible via `created_by`), but it is the one place a future unverified-ghost id could vanish from a client read. **Fix direction:** verify `useMySoloEntries` never needs to render an unverified ghost; otherwise route it through a service-role edge fn. Flagged for confirmation, not a known break.

## Medium (fix when convenient)

1. **Screenshot path extracts the restaurant twice and double-spends on Google Places** — `supabase/functions/resolve-url/index.ts:488` (`handleVisionExtract`, inline) computes a full extraction + Places lookup + candidates, but `ImportLinkSheet.tsx:289` discards those candidates and jumps to the DestinationPicker; on confirm, `create_import` fires `resolve-url[action=extract]` which extracts and resolves **again** (`handleAsyncExtract` → `upsertRestaurantFromExtracted`, which can call `callPlacesSearch` up to 2×). The vision step is cache-deduped via content-hash, but the **Places lookups are not** — a single screenshot save can incur up to 3 Places calls. The ticket explicitly named Places (~1.7¢/lookup) as the expensive API to watch. The inline path's resolved name also never reaches the user before they confirm (the card shows "reading it…" even though extraction already ran). **Fix direction:** either skip the inline `handleVisionExtract` for the screenshot path (go straight to DestinationPicker, let the async job do the one-and-only extraction), or carry the inline result into `create_import` so the async path short-circuits.

2. **`fn_detect_and_surface_float` swallows all exceptions, triply** — `supabase/migrations/20260603000800_fix_pass2.sql:137` (`WHEN others THEN NULL`), plus the caller wraps it in `.catch(() => null)` and an outer try/catch (`supabase/functions/resolve-url/index.ts:856, 863`). Matches the "best-effort, never block the save" doctrine, but if the float never surfaces there is **zero diagnostic signal** anywhere — a silent feature. Given floats are "the star" mechanism, a swallowed error here is invisible. **Fix direction:** at minimum `RAISE WARNING` (instead of `NULL`) inside the SQL exception block, or have the caller log when the RPC errors, so a non-firing float is debuggable. Needs verification that floats actually surface in prod (the float UPSERT path is `NOT RUN` in tests — see Metrics).

3. **Digest child `I'm-in` reactions don't update optimistically** — `napkin-app/hooks/posts/usePostInteractions.ts:267` (`flipItem` walks top-level activity items where `item.id === targetId`). Digest children are nested inside `share_digest.childShares` (`supabase/functions/table-activity/index.ts:537`), not top-level items, so tapping "i'm in" on a child inside an expanded `ShareDigestCard` toggles the server row but the count/active-state won't reflect until a refetch. Cosmetic; reconciles on `onSuccess` invalidate. **Fix direction:** extend `flipItem` to also descend into `childShares`, or accept the refetch.

4. **`top_emojis` is a `text[]` for `table_share` but an object-array (`jsonb`) for entries/nights — the shared `patchTopEmojis` helper silently produces a malformed mixed array** — `supabase/migrations/20260603000300_table_shares.sql:20` declares `top_emojis text[]`; `useToggleReaction.onMutate`'s `flipItem` calls `patchTopEmojis(item.top_emojis ?? [], ...)` (`napkin-app/hooks/posts/usePostInteractions.ts:279`), which expects `EmojiCount[]` (objects with `.emoji/.count/.last_reacted_at`). For a `shared_save` item, `item.top_emojis` is `['👀']` (strings), so `patchTopEmojis` finds no match and appends an object — yielding `['👀', {emoji,count,...}]`. Harmless today **only because `SharedSaveCard` never renders `topEmojis`** (it shows just the count). A latent landmine if any share card later renders top emojis. **Fix direction:** normalize the two shapes, or have the share branch skip `patchTopEmojis`.

5. **The `extraction.byHash` / `floats.detail` / `tableShares.detail` / `importJobs.*` query keys are registered but never read** — `napkin-app/lib/queryKeys.ts:184-202`. `importJobs.all/detail`, `tableShares.forTable/detail`, `floats.forTable` (read in `useDismissFloat.onSuccess` invalidate only), `floats.detail`, and `extraction.byHash` have no `useQuery`/`useInfiniteQuery` consumer — they were added speculatively. Not a bug; dead surface area that implies query hooks that were planned and not built (e.g. no `useImportJob(jobId)` polling hook — the pending card resolves only via the wishlist/activity invalidations, never via a job-status poll). **Fix direction:** delete the unused keys, or note them as reserved.

## Low (nice to have)

1. **The "no more `as any`" comment in the feed dispatcher is false — two casts remain** — `napkin-app/app/(tabs)/tables.tsx:760` claims the `shared_save` branch is fully typed, but `:768` (`(s as any).shareId`) and `:772` (`(s as any).note`) still cast. The fields actually exist on `SharedSaveActivityItem` (`shareId?`, `note?`), so the casts are unnecessary and the comment is misleading. **Fix:** drop the casts; read `s.shareId ?? s.id` and `s.note` directly.

2. **Duplicated parallel type for digest children** — `SharedSaveCardShapeForDigest` (`napkin-app/hooks/tables/useTableActivity.ts:156`) and `DigestChildShare = SharedSaveCardProps` (`napkin-app/components/feed/ShareDigestCard.tsx:28`) describe the same shape independently. tsc passes (structurally compatible) but they will drift. **Fix:** have the hook import `SharedSaveCardProps` as the child type.

3. **Unverified ghosts are never deduped per user — repeat unresolvable captures spam the wishlist with distinct ghost rows** — `supabase/functions/resolve-url/index.ts:421,472` mint `external_id = ghost_${userId}_${Date.now()}` (unique per call). Two captures of the same name-only spot create two ghost `restaurants` rows and two wishlist rows. Avoids the Critical-1 unique collision (good) but leaves duplicate ghosts. **Fix:** dedup ghosts by `(created_by, lower(name), city)` before insert.

4. **Screenshot/vision saves can't attach a note to their Table share card** — `napkin-app/components/wishlist/ImportLinkSheet.tsx:454` (`handleDestinationConfirm` passes `destinations` but no `note`; `DestinationPicker` has no note field). The schema (`table_shares.note`) and `SharedSaveCard` both support a note, and `create_import` accepts one — it's just never collected on the screenshot path. **Fix:** add an optional note field to the DestinationPicker, or accept the gap.

5. **Pre-existing `callEdgeFn`-bypass debt (outside TICKET-060)** — `napkin-app/hooks/tables/useCreateEntry.ts:131` and `napkin-app/app/create-entry.tsx:223,375` call `supabase.functions.invoke` directly; `napkin-app/hooks/restaurants/useRestaurantPage.ts:168` and `napkin-app/hooks/feed/useFeed.ts:75` raw-`fetch` an edge-function URL. CLAUDE.md mandates `callEdgeFn` for all edge calls (auth attachment + structured-error envelope). These predate TICKET-060 and didn't regress, but they're the exact drift CLAUDE.md warns about. **Fix:** migrate to `callEdgeFn` opportunistically.

6. **Migration `20260603000600` created a dead `sync_post_counts()` function** — the live triggers call `sync_post_counts_and_top_emojis()` (`20260418000000_post_interactions.sql:226`), not `sync_post_counts()`. Migration 600's entire function-3 body (`supabase/migrations/20260603000600_post_interactions_table_share_target.sql:44-184`) is never invoked; `fix_pass1` correctly patched the *live* function instead. Harmless (it didn't clobber a live function — the name is unused elsewhere) but it's wasted/confusing migration weight that future readers may mistake for the active path. **Fix:** drop the dead `sync_post_counts` definition, or comment that it's intentionally unused.
